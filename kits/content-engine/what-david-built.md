# What David Built

This page is for hiring managers, recruiters, and the leaders who sign off on a content program. It says what problem David Luther set out to solve inside an in-house B2B marketing team, what he built, and what it shows about how he works.

## The problem

A B2B content team runs many pages through a CMS, pays for several SEO and analytics platforms, and answers to leaders who ask a simple question: how do we know it worked. The honest answer is usually uncomfortable. Topics get briefed that a colleague already covered. A statistic gets repeated from a summary of a summary. Platforms point in different directions and the loudest one wins. A scheduled pull quietly stops running, and a week passes before anyone notices because older data still looks fine.

The knowledge of how to do each stage well lives in a few people's heads, so the quality depends on who happens to be on shift.

## What David built

While running search and content work in-house at Corpay, David Luther treated content as a pipeline with gates, not a calendar of posts. He built the pipeline as small, separate skills, each doing one job and handing a file to the next, with a named person making each judgment call.

- **A cheap screen before the expensive stage.** Candidate topics are checked against what exists, what is planned, each other, and a demand floor before anyone writes a brief. The screen reports what it couldn't check instead of calling it clean.
- **One author for briefs.** A single skill writes every brief, with a required verdict, a redundancy check, and statistics that must name a source. Drafting refuses to start without a complete brief.
- **Quality and evidence gates.** Drafts pass a style check, an AI-habit score calibrated to the team's own pages, and a lint for the words a site actually shows. Anything that reaches a leader passes an evidence review that grades every claim and requires a dated source for every number.
- **A publish step that stops for a person.** Publication means the approved change, the confirmed live deployment, and the live page showing its own title. A schedule never publishes.
- **A measurement rhythm that changes decisions.** Pages are checked at set points, refreshes are ranked from search data, and a refresh has to change something real. Where platforms disagreed, the rule was to name the sources and the reason before acting, not to average.
- **Failures written down, same day.** Every scheduled job leaves a record, retries once, and trips a check when it misses its slot. A quiet week and a broken job no longer look the same.

Then he generalized the method into this open kit, removing everything specific to one company, so another team can run it with its own platforms, CMS, and reporting cadence.

## What it changed

Work that depended on a few experienced people became a repeatable process that a new hire can follow and a manager can audit. Duplicate and low-value topics were stopped earlier. Unsupported statistics were caught before publication instead of after a complaint. Decisions about what to update were tied to data with a named source, and leader updates said what had been measured and what had deliberately not been claimed. The team spent less time arguing about whose number was right, because the rule for conflicts was written down before the argument started.

## Skills this shows

- **Program design.** Turning a loose content calendar into a staged pipeline with owners, handoffs, and refusal rules.
- **Measurement discipline.** Grading evidence, naming sources, reconciling platforms that disagree, and refusing to claim a cause the data can't support.
- **Automation with honesty.** Deciding what can run unattended, what must have a person present, and building the log and alarm so failures can't hide.
- **AI-search and search strategy.** Intent, structure, and answer-friendly pages without overpromising rankings.
- **Writing systems.** A style guide turned into checks a program can run, calibrated to a team's own work.
- **Technical writing for mixed audiences.** Setup guides with step IDs, problem codes, and a check-up, so a team can run the method without the author in the room.
- **Cross-functional communication.** Giving leaders a one-page answer with the source line behind every number.
